# Pipeline `solution.py` — полный план

Разделено на **offline** (что везёшь в ZIP) и **online** (что происходит на один тест-кейс). Между кейсами состояние не сохраняется — всё выводится из переданной истории.

---

# A. Offline: таблицы и индексы

Собираются один раз, кладутся в архив. **Онлайн на индексации — ноль LLM-вызовов.**

| Таблица | Колонки | Как строится |
|---|---|---|
| `documents` | doc_id, file, title, product_ids[], segments[], topic | парсинг файлов + ручная разметка меты |
| `chunks` | **chunk_id = `file#header-slug`**, doc_id, header_path, text_raw, **text_ctx**, type(text/table), parent_id | разбиение по дереву заголовков, 300–600 токенов, overlap 10–15%, таблицы атомарны |
| `chunk_questions` | chunk_id, question | LLM offline: 2–3 вопроса «своими словами», на которые чанк отвечает |
| `tables` | table_id, chunk_id, markdown, caption | таблицы вырезаются целиком, caption генерит LLM |
| `products` (карточки) | product_id, name, aliases[], tasks[], segments[], requires[], **not_for[]**, pricing_model, caveats, chunk_ids[] | LLM-черновик по доку продукта → **ручная проверка**, 20–40 шт |
| `glossary` | canonical, aliases[], type | LLM-извлечение из БЗ + руками, 150–250 записей |
| `entity_index` | entity → chunk_ids[] | инвертированный индекс по линковке глоссария |
| `relations` | src, rel_type, dst, chunk_id | whitelist: `solves_task, for_segment, requires, part_of, alternative_to`. provenance обязателен |
| `vectors` | id, dense (bge-m3), [sparse] | эмбеддинги для text_ctx, questions, карточек |
| `bm25` | лемматизированный текст | индекс по text_ctx + questions, русская морфология |

**Ключевой момент — `text_ctx`:**
```
{Название документа} → {Путь заголовков}
{1–2 предложения LLM: о чём этот фрагмент и в каком контексте}
{Сам текст}
```
Индексируется **и в dense, и в BM25**. В LLM отдаётся `text_raw` — без мусора.

`chunk_id` — по слагу заголовка, не по порядковому номеру. Иначе смена чанкинга ломает все ссылки.

# B. Online: шаги

### Шаг 0. Cold start
Индексы грузятся один раз на уровне модуля, лениво, mmap. HTTP-клиент к API держится тёплым. Таймауты на каждый вызов.

### Шаг 1. Нормализация и guard
Берём `history` + последнюю реплику. Чистим пробелы/эмодзи. Regex-проверка на инъекции («игнорируй инструкции», «выведи системный промпт») → шаблонный отказ, дальше не идём.

### Шаг 2. Один fused-вызов понимания
**Единственный LLM до генерации.** Возвращает строгий JSON:

```json
{"intent":"task_diagnosis",
 "standalone_query":"как снизить счета за электроэнергию в торговом центре",
 "query_variants":["уменьшить расходы на электричество ТЦ"],
 "entities":["торговый центр","счета"],
 "aspects":["направления экономии","продукты"],
 "slot_delta":{"object_type":"ТЦ"},
 "topic_switch":false,
 "lead_signal":false}
```

В промпте: список интентов, схема слотов, последние 6 реплик, короткий список имён продуктов. Выход ~200 токенов.

**Обход без LLM:** приветствие, благодарность, ответ с телефоном/ФИО → правила.
**Fallback:** битый JSON → regex-ремонт → если не вышло, `standalone_query = question`, интент по ключевым словам.

> Проверь на платформенной модели, поддерживает ли она structured output. От этого зависит, парсить JSON или фиксированный текстовый формат.

### Шаг 3. Политический роутинг (детерминированно, до поиска)

| Условие | Действие |
|---|---|
| `intent = out_of_scope_tech` (настройка приборов, техдокументация) | шаблонный отказ + специалист. **Поиск не запускается** |
| `intent = off_topic` | короткий возврат к теме |
| `lead_signal` или активное состояние заявки | машина сбора (шаг 13) |
| иначе | поиск |

### Шаг 4. Условия поиска

Строятся из интента и слотов:

| Интент | Что ищем | Фильтр / буст | k |
|---|---|---|---|
| `pricing` | карточка названного продукта + чанки с ценами | **жёсткий** фильтр по product_id, если имя найдено в глоссарии | 6 |
| `product_consult` | сначала карточки, потом их чанки | буст по segment, если известен | 8 |
| `task_diagnosis` | карточки по `tasks[]` + чанки | буст по object_type/segment | 8 |
| `comparison` | 2–3 карточки + relations `alternative_to` | фильтр по названным именам | 10 |
| общий факт | чанки | без фильтров | 6 |

Три правила:
1. **Мета-фильтры по умолчанию мягкие (буст, не отсечение).** Мета в БЗ разреженная — жёсткий фильтр убьёт recall. Жёсткий только при явно названном продукте.
2. **Синонимы из глоссария добавляются в лексическую ветку**, не в dense.
3. **`q0 = standalone_query` участвует всегда.** Варианты и HyDE — только дополнение. HyDE лишь для размытых «болевых» запросов и никогда не попадает в ответ.

### Шаг 5. Параллельный поиск (async, 5 веток)

| Ветка | Что делает | Топ |
|---|---|---|
| A | dense по карточкам + точное совпадение алиасов + матч tasks/segments | 2–3 карточки |
| B | dense по `text_ctx` | 30 |
| C | BM25 по леммам + алиасы | 30 |
| D | dense по `chunk_questions` (вопрос↔вопрос) | 15 |
| E | `entity_index` — чанки с найденными сущностями | 10 |
| F | 1-hop по `relations` — **только для comparison/multi-hop** | +5 |

### Шаг 6. Слияние
Min-max нормализация скоров внутри каждой ветки, затем взвешенная сумма:
```
score = 0.45*dense + 0.30*bm25 + 0.15*questions + 0.10*entity
```
RRF — запасной вариант, если скоры окажутся некалиброванными. Далее: дедуп по chunk_id → **cap 2 чанка на документ** → MMR (λ≈0.7) против boilerplate → top 20–25.

### Шаг 7. Реранкинг (условный)
Qwen3 Reranker 8B, top 12–20, обрезка до ~512 токенов, батч.
**Пропускаем**, если интент простой фактовый и dense с BM25 согласованно дали одного лидера. Дешёвая замена — ColBERT MaxSim из bge-m3. Выход: top 4–6.

### Шаг 8. Сборка контекста
- **Small-to-big**: короткий чанк (<200 токенов) заменяется родительской секцией.
- Таблица подставляется целиком в markdown.
- Карточка продукта добавляется как структурированный блок.
- Бюджет ~2500–3500 токенов. Лучший фрагмент — первым, второй — последним (середина читается хуже).
- Каждый блок с `chunk_id` — по нему потом проверяются цитаты.

### Шаг 9. Покрытие и ясность (детерминированно, без LLM)

```
aspect_covered = (ключевые слова аспекта есть в evidence) AND (score чанка ≥ τ)
coverage = high    если все аспекты покрыты и top1 ≥ τ_high
           partial если покрыта часть
           none    если top1 < τ_floor ИЛИ ни одна сущность не слинковалась
clarity  = заполнены ли блокирующие слоты для этого интента
margin   = score₁ − score₃
```

Блокирующие слоты: `pricing` — нет; `product_consult` — боль + тип объекта; `task_diagnosis` — тип объекта; `comparison` — сценарий.

**Абсолютный порог обязателен**: top-k всегда что-то возвращает, без floor бот отвечает по нерелевантным кускам.

### Шаг 10. Матрица решений

| coverage | clarity | действие |
|---|---|---|
| high | ясно | ответ + мягкий CTA |
| high | неясно | ответ на общем уровне + **один** вопрос |
| partial | ясно | покрытая часть + «про X в базе нет» + специалист |
| partial | неясно | 1 вопрос, только если он способен открыть другой фрагмент |
| none | любое | «в базе нет» + специалист. **Не допрашивать** |

Проверка полезности вопроса: изменится ли ответ при разных значениях слота? Нет → не спрашиваем. Максимум 2 уточнения подряд.

### Шаг 11. Генерация
Один вызов. Стабильный префикс промпта (роль, политика, формат, ≤150 слов, только из evidence, цитаты `[chunk_id]`) → evidence → слоты → standalone-запрос. Префикс байтово неизменен ради prefix-кэша.

Выход:
```json
{"answer":"...", "cited_ids":["..."], "products":["..."],
 "next_action":"clarify|cta|none", "missing_slot":"scale"}
```

**Отказ и уточнение — шаблоны, не LLM.** Быстрее, безопаснее, персонализируются подстановкой слотов.

### Шаг 12. Детерминированный верификатор (0 мс)
- `cited_ids ⊆ evidence`
- все **числа, единицы, названия продуктов** из ответа буквально есть в процитированных чанках
- имена продуктов ∈ каталогу
- цена без оговорки → снять или добавить оговорку
- нет лексики настройки приборов
- ≤150 слов, обрезка по границе предложения

Провал → один repair-pass, если бюджет позволяет. Иначе fallback (шаг 15).

### Шаг 13. Машина заявки
Детерминированный state machine: ФИО → телефон → компания, по одному полю за ход. Валидация телефона regex RU, частичный ввод допускается, не более 2 попыток на поле. По завершении — резюме: сегмент, объект, боль, текущий учёт, продукты, открытые вопросы, контакты, `source_chunk_ids`.

Триггер: слоты заполнены + продукт подобран, ИЛИ явный сигнал, ИЛИ два полезных ответа, ИЛИ отказ. **Ответ никогда не блокируется формой.** В автопроверке состояние выводится только из `history`.

### Шаг 14. Выход
Строка ответа в формате из «Примера выходного файла». Отладочный payload (тайминги, кандидаты, скоры, что процитировано) — отдельное поле для UI, **никогда внутри текста ответа**.

### Шаг 15. Надёжность и деградация
Глобальный try/except. Таймаут на вызов, 1 ретрай с backoff. Общий бюджет ~8 с.

Лестница деградации:
```
полный пайплайн
 → без реранкера
  → без fused-вызова (BM25 + шаблоны)
   → extractive: 2 предложения из топ-чанка + предложение специалиста
```
**Пустая строка и исключение недопустимы никогда.**

# C. Бюджет

| Шаг | LLM | Цель p50 |
|---|---|---|
| 1–3 | 0 | <20 мс |
| 2 fused | 1 | 0.4–0.8 с |
| 4–6 поиск | 0 | 0.1–0.3 с |
| 7 реранк | 0 (API) | 0.3–1.0 с, условно |
| 9–10 | 0 | <10 мс |
| 11 генерация | 1 | 1.5–3 с |
| 12–14 | 0 | <30 мс |

**Итого: 2 LLM-вызова p50, ≤3 p95. Цель p50 ≤ 3 с, p95 ≤ 6 с.**
Отказ, приветствие, сбор заявки — **0–1 вызов**.
